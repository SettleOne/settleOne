PART 5 — SMART CONTRACT INTEGRATION MAP
================================================================================

Every button in the frontend maps to an exact smart contract call.

WORKSPACE: Creating a Deal
  Button: "Create Deal" → confirm in modal
  Contract: DealManager.createDeal(DealInput)
  Required wallet state: connected, correct network
  Pre-flight: token whitelist check (read tokenConfigs)

WORKSPACE: Funding a Deal
  Button: "Fund Deal" / "Fund 60% Now" / "Fund Remaining 40%"
  Contract: DealManager.fundDeal(dealId, amount) + ERC20.approve(vault, amount)
  Required wallet state: connected, correct network, correct wallet (buyer only)
  Pre-flight: balance check, allowance check, vault.isFullyFunded check

WORKSPACE: Accepting a Deal (as Seller)
  Button: "Accept Deal"
  Contract: DealManager.acceptDeal(dealId)
  Required wallet state: connected

WORKSPACE: Rejecting a Deal (as Seller)
  Button: "Reject Deal"
  Contract: DealManager.rejectDeal(dealId, reasonHash)
  Pre-flight: reasonHash = keccak256(reason text)

WORKSPACE: Extend / Cancel Seller Window (as Buyer)
  Button: "Extend Window" or "Cancel Deal"
  Contract: DealManager.expireSellerAcceptance(dealId, extendDeadline, newWindow)
  Note: if extendDeadline=false AND depositedFunds > 0 → refund triggered

WORKSPACE: Submitting Delivery (as Seller)
  Button: "Submit Delivery"
  Flow:
    1. Upload files → IPFS → get CIDs
    2. Compute proofHash = keccak256(all CID hashes concatenated)
    3. Call DeliveryManager.submitDeliveryProof(dealId, proofHash, primaryCID, evidenceType, submissionData, bytes(""))

OPERATIONS: Approving Delivery (as Verifier)
  Button: "Approve Delivery"
  Flow:
    1. Backend generates DeliveryApproval EIP-712 message
    2. Verifier signs message (validUntil = now + 15 minutes)
    3. Call DeliveryManager.finalizeDelivery(dealId, encodedVerificationData)

WORKSPACE: Accepting Delivery (as Buyer)
  Button: "Accept Delivery"
  Pre-flight: vault.isFullyFunded(dealId) must be true
  Contract: DeliveryManager.acceptDelivery(dealId)

WORKSPACE: Requesting Revision (as Buyer)
  Button: "Request Revision"
  Contract: DeliveryManager.requestRevision(dealId, keccak256(reason), keccak256(evidence))

WORKSPACE: Raising Dispute (as Buyer or Seller)
  Button: "Raise Dispute"
  Flow:
    1. Upload evidence files → IPFS → get evidence CID
    2. evidenceHash = keccak256(evidence CID)
    3. Call DeliveryManager.raiseDispute(dealId, keccak256(reason), evidenceHash)

WORKSPACE: Cancelling Dispute (as opener)
  Button: "Cancel Dispute"
  Contract: DeliveryManager.cancelDispute(dealId)

OPERATIONS: Resolving Dispute (as Arbitrator/Resolver)
  Button: "Issue Verdict"
  Flow:
    1. Upload resolution report → IPFS → get CID
    2. resolutionHash = keccak256(resolution CID)
    3. SimpleResolver.decide(dealId, outcome, sellerAward, resolutionHash)
    4. Then: DeliveryManager.resolveDispute(dealId, resolverData)
    Note: Steps 3+4 combined in the UI as one transaction bundle

AUTOMATION (no button, internal):
  AutomationHandler.performUpkeep() called by Chainlink
  Actions: FinalizeDelivery | AutoAcceptDelivery | ReleaseSeller | RefundBuyer

PART 6 — AUTHENTICATION & SECURITY

[ ] Auth flow (implemented in both workspace and operations):
    1. User enters email + password (or Google OAuth)
    2. POST /auth/login → returns { accessToken, refreshToken, user }
    3. If OTP required (for staff): show OTP step
    4. Store accessToken in memory (NOT localStorage — XSS risk)
    5. Store refreshToken in httpOnly cookie
    6. On every API call: send accessToken in Authorization header
    7. On 401: attempt refresh, if fail → redirect to /login
    8. Role check: if user.role !== expected for app → redirect

[ ] Wallet binding:
    1. After login, user connects wallet
    2. Backend issues a nonce: GET /auth/wallet-nonce
    3. User signs: "Sign this to link your wallet to SettleOne: {nonce}"
    4. POST /auth/link-wallet with signature
    5. Backend verifies + links wallet address to user account

[ ] Deal access permissions (enforced server-side AND client-side):
    All deals: read metadata, read state, read activity feed
    Deal files: buyer + seller + verifier + resolver + admin ONLY
    Chat room: buyer + seller ONLY
    Verdict panel: resolver ONLY
    Vault controls: vault admin ONLY

PART 9 — KEY BUSINESS RULES (frontend must enforce)
================================================================================

1. Fund Deal:
   - Only deal.buyer can fund
   - Stage 0: min 60% of deal.amount
   - Stage 1: remaining 40%, ONLY callable when deal.state == AwaitingAcceptance
   - Full amount in one shot always allowed
   - Cannot over-fund (depositedFunds + amount must not exceed deal.amount)

2. Accept Deal:
   - If deal.seller == 0x0: any connected wallet can accept
   - If deal.seller != 0x0: only that specific wallet can accept
   - Only callable in PendingSellerAcceptance state

3. Submit Delivery:
   - Only deal.seller can submit
   - Only in Active or DeliverySubmitted (re-submit after rejection) state
   - Cannot re-submit if previous state is Pending (not yet rejected)
   - Cannot submit after deliveryDeadline

4. Accept Delivery (Buyer):
   - vault.isFullyFunded(dealId) must be true first
   - Only callable in AwaitingAcceptance state
   - Within acceptanceWindowEndsAt
   - If buyer is silent: automation auto-accepts after window (if fully funded)

5. Raise Dispute:
   - Buyer OR seller can raise
   - Only in AwaitingAcceptance or Accepted state
   - Within the respective window (acceptanceWindow or disputeWindow)

6. Resolve Dispute:
   - Only the deal's deal.disputeResolver address can resolve
   - Must be in Disputed state
   - Arbiter calls SimpleResolver.decide() first, then resolveDispute()

7. Cancel Deal:
   - Only buyer can cancel
   - Only before Active state (AwaitingFunding or PendingSellerAcceptance)
   - If funds deposited, automatic refund triggered

8. Extend / Cancel Seller Window:
   - Only buyer can call
   - Only in PendingSellerAcceptance state AND after sellerAcceptanceDeadline passed
